# Headless Secret Service on box

## Recommendation

GNOME Keyring can support the existing `chezmoi secret keyring` call. For unattended use after a reboot, box also needs a way to unlock the keyring without a human. A machine-held unlock credential permits that, but a compromised running host can unlock the collection. An empty keyring password provides no protection at rest. Neither approach prevents Google from requesting a challenge that the password helper cannot answer.

For a single service, a systemd encrypted credential is an alternative. The existing age setup avoids a new daemon but leaves an age identity on disk. The selected approach stores `GCLOUD_PASS` in the age-managed `~/.secrets` file and uses it in the gcloud helper.

## Activation, unlock and boot

- Chezmoi uses [go-keyring for GNOME Keyring on Linux](https://www.chezmoi.io/user-guide/password-managers/keychain-and-windows-credentials-manager/). GNOME Keyring 46.1's [D-Bus activation file](https://github.com/GNOME/gnome-keyring/blob/46.1/daemon/org.freedesktop.secrets.service.in) registers `org.freedesktop.secrets` and starts the secrets component on demand. A client needs the intended user's session bus; starting a private bus for one command does not establish a shared service for other sessions.
- Activation starts the service, not an unlocked collection. A locked collection can require a prompt, and a headless process may be unable to answer it. GNOME's [PAM documentation](https://wiki.gnome.org/Projects%282f%29GnomeKeyring%282f%29Pam.html) says PAM unlocks the login collection with the entered login password when configured. SSH public-key login and unattended boot do not supply that password. PAM configuration and keyring password matching both matter.
- Ubuntu 24.04's [daemon manual](https://manpages.ubuntu.com/manpages/noble/man1/gnome-keyring-daemon.1.html) documents `--unlock`: it reads the password from standard input and unlocks or creates the login keyring. `--login` also reads stdin but requires later initialization with `--start`. Avoid placing the password in command arguments, environment variables, logs, or shell history. The default collection must be the intended persistent login collection; unlocking a different collection does not guarantee client access.
- Persistent keyrings are encrypted files in the user's home; the separate session keyring is never written to disk ([GNOME](https://help.gnome.org/system-admin-guide/processes.html), [upstream README](https://github.com/GNOME/gnome-keyring/blob/main/README)). Disk persistence does not preserve unlocked state after daemon exit or reboot. A lingering systemd user manager can start at boot and survive logout ([systemd 255 loginctl](https://www.freedesktop.org/software/systemd/man/255/loginctl.html)), but it does not provide an unlock password. Boot order, shared session bus, daemon startup, unlock, and failure/recovery need testing together.
- The [Secret Service specification](https://specifications.freedesktop.org/secret-service/latest-single/) does not mandate application-level access control. Treat an unlocked collection as available to processes able to use that user's bus, including compromised same-user agents. Root and the VPS host are also in the trust boundary; encryption at rest does not protect a running unlocked service from them.

## Alternatives and tradeoffs

- **Encrypted systemd credentials:** Ubuntu's [systemd 255 manual](https://manpages.ubuntu.com/manpages/noble/man1/systemd-creds.1.html) describes authenticated encryption with a root-owned host key, a TPM2-derived key, or both. `LoadCredentialEncrypted=` decrypts at service activation and exposes a credential file to the service ([systemd 255 exec](https://www.freedesktop.org/software/systemd/man/255/systemd.exec.html)). A host key stored on the same disk is weaker against a full offline disk copy than a usable TPM; neither protects against an attacker controlling the running service or root. TPM and host binding complicate migration and recovery. Do not assume the VPS offers a usable TPM.
- A root-managed system service could deliver an unlock password or the individual secret to a dedicated process, subject to its privileges and deployment design. This is not a drop-in Secret Service backend. Current upstream documents `systemd-creds --user` for user-scoped encrypted credentials as [added in version 256](https://www.freedesktop.org/software/systemd/man/256/systemd-creds.html); box reports systemd 255.4. Do not assume a newer user-manager recipe works on noble. Test any proposed system-to-user handoff and isolation before relying on it.
- **Existing age setup:** [`run_onchange_before_decrypt-private-key.sh.tmpl`](../../run_onchange_before_decrypt-private-key.sh.tmpl) decrypts the repository's passphrase-protected `key.txt.age` once to `~/.config/chezmoi/key.txt` and sets mode `0600`. The [README](../../README.md) describes the first-apply prompt. Later use depends on the on-disk private identity, so this trades a running keyring for a readable-at-rest file accessible to that user and root. Age-encrypted source files still need secure recovery of the passphrase and identity; using the existing identity to store another password does not add a new independent security boundary.

## Google reauthentication

The work configuration defines `gcloud-auth-check` and `gcloud-reauth`. The latter runs gcloud under Expect and reads `GCLOUD_PASS` from `~/.secrets`. The DB tasks call that helper when token retrieval reports reauthentication is required. An earlier isolated test confirmed that the original helper could answer a synthetic password prompt using a synthetic secret in GNOME Keyring.

The installed gcloud credential code checks whether it can prompt before calling Google Auth's reauth flow. [Google Auth's upstream reauth code](https://github.com/googleapis/google-auth-library-python/blob/main/google/oauth2/reauth.py) checks for an interactive stdin and its [password challenge](https://github.com/googleapis/google-auth-library-python/blob/main/google/oauth2/challenges.py) calls `getpass`; simply piping a password is not a reliable headless integration. A helper that changes prompt or challenge behavior depends on implementation details and must be reviewed against the installed SDK version. A password cannot satisfy every challenge: security keys need a device and user presence, and SAML requires a browser login. Storing a human Google password for unattended use also increases the impact of a box compromise and may conflict with organizational policy.

Workspace administrators can require reauthentication on a fixed [1 to 24 hour schedule](https://knowledge.workspace.google.com/admin/security/set-session-length-for-google-cloud-services), including security-key or password challenges. For a third-party IdP, Google documents `gcloud auth login` for password reauthentication. On a headless host, Google's [`--no-browser` remote-bootstrap flow](https://docs.cloud.google.com/sdk/gcloud/reference/auth/login) uses gcloud and a browser on another trusted machine; `--no-launch-browser` is another documented interactive flow. Keep authorization URLs and codes private. User ADC is separate and may require `gcloud auth application-default login` when its session expires ([Google](https://docs.cloud.google.com/docs/authentication/reauthentication)). For unattended workloads, prefer a suitable attached service account or workload identity federation where available ([Google authentication guidance](https://docs.cloud.google.com/sdk/docs/authenticate)).

## Box checks

On 2026-10-29, box had a user D-Bus session and lingering enabled, but no registered or activatable `org.freedesktop.secrets` service. Ubuntu reported `gnome-keyring` as not installed. Systemd 255.4 does not support `systemd-creds --user`, and `systemd-creds has-tpm2` reported partial support, not a usable TPM.

An isolated D-Bus session used an extracted Ubuntu GNOME Keyring package and synthetic secrets. Chezmoi stored and retrieved an item, retrieval failed after a daemon restart without an unlock, and retrieval worked after unlocking the same keyring in a new session. The existing Expect helper also answered a synthetic gcloud password prompt. No package, credential, PAM setting, cloud setting, or login session on box was changed.

That test did not reboot box or test systemd's system-to-user credential handoff. After switching to `~/.secrets`, the DB tunnel invoked the reauthentication helper and opened successfully on box; a staging `SELECT 1` also succeeded. The helper suppresses prompt output, so this does not independently confirm which Google challenge appeared. A reboot and the macOS flow remain untested.
